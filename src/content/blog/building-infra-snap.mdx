Most teams don't start with infrastructure-as-code. They start with a console, a few clicks, and a deadline. `infra-snap` is my attempt to make the jump from "clicked-together AWS account" to "clean Terraform" a lot less painful.

## The problem with importing existing infra

Terraform's own `import` command is powerful but tedious. You have to write the resource block *first*, then import state into it, one resource at a time. For an account with a few hundred resources, that's a bad afternoon.

The core idea behind `infra-snap` is simple: read what's actually running, and generate both the resource blocks **and** the import statements for you.

## How it works

There are three stages to a snapshot.

### 1. Discovery

We walk the account using the AWS SDK, one service at a time, and normalize everything into a flat list of resources with a provider type and an ID.

```go
type Resource struct {
    Type string // e.g. "aws_s3_bucket"
    ID   string // e.g. "my-logs-bucket"
    Tags map[string]string
}
```

Discovery is read-only. `infra-snap` never mutates your account — worst case it's a slow, polite `List*` caller.

### 2. Codegen

For each resource we emit an HCL block. The trick is that we only write attributes Terraform actually needs; everything else is left for `terraform plan` to reconcile against the real world.

### 3. Import blocks

Since Terraform 1.5 you can declare imports in config instead of running the CLI command per-resource:

```hcl
import {
  to = aws_s3_bucket.my_logs_bucket
  id = "my-logs-bucket"
}
```

`infra-snap` generates one of these per discovered resource, so a single `terraform plan` tells you exactly how far your generated config drifts from reality.

## What I learned

- **Tags are gold.** Grouping resources by their `Environment` / `Service` tags let me generate sensible file and module boundaries automatically.
- **Rate limits are real.** Naive concurrent `List*` calls will get you throttled fast; a token-bucket limiter per service made discovery predictable.
- **Perfect is the enemy of committed.** The goal isn't 100% accurate Terraform — it's config that's *good enough to commit*, so the rest can happen in normal PR review.

## Where it's going

Next up is a diff mode: point `infra-snap` at an account **and** an existing Terraform state, and have it report only the resources that were created out-of-band. That's the drift-detection story I actually care about.
