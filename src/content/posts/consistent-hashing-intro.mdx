Say you run a pizza shop with 3 delivery riders. You assign each order to a rider by `order_id % 3`. Simple. Then you hire a fourth rider, switch to `% 4`, and suddenly *almost every* order gets reassigned to a different person. Chaos.

That's exactly what happens to a distributed cache when you add or remove a node. Consistent hashing is the fix.

## The problem with modulo

With `hash(key) % N`, changing `N` remaps nearly every key. In a cache, that means a near-total cache miss storm the moment you scale. Not great.

## The ring

Consistent hashing puts both **keys** and **nodes** onto the same circular hash space — imagine a clock face from 0 to 2³².

- Each node is hashed to a point on the ring.
- Each key is hashed to a point on the ring, then walks clockwise to the first node it meets.

When you add a node, only the keys between it and its predecessor move. Remove a node, and only *its* keys shift to the next one clockwise. Everything else stays put — roughly `1/N` of keys move instead of nearly all of them.

## Virtual nodes

One catch: with few nodes, the ring gets lumpy and load is uneven. The fix is **virtual nodes** — hash each physical node to many points on the ring (say 100–200). Now load smooths out, and a node leaving spreads its keys across many others instead of dumping them all on one neighbor.

## Where you'll see it

- Distributed caches like Memcached clients and Redis Cluster
- Databases like Cassandra and DynamoDB for partitioning
- Load balancers that need sticky-ish routing without a central table

It's one of those ideas that feels obvious in hindsight and quietly powers a huge amount of infrastructure.
